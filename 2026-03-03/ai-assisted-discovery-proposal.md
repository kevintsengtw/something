# AI 輔助 Discovery → 結構化測試情境：可行方案

## 一、問題背景與核心命題

### 1.1 現況：下游已通，上游未接

dotnet-testing-orchestrator 已建構完成的能力鏈：

```
Analyzer（分析 SUT）→ Writer（撰寫測試）→ Executor（執行測試）→ Reviewer（審查品質）
```

這條鏈解決了「怎麼寫測試」和「怎麼跑測試」的問題，但存在兩個根本性的缺口：

- **輸入缺口**：orchestrator 的輸入僅有程式碼，缺乏結構化的測試情境、業務規則與驗收條件，導致 AI 只能從程式碼結構推測該測什麼，而非從需求規格驅動。
- **審查缺口**：Reviewer agent 只能檢查「測試程式碼寫得好不好」，無法回答「測試有沒有測到該測的東西」，因為它手上沒有「該測的東西」這份對照清單。

### 1.2 柯仁傑的論述脈絡

柯仁傑（kojenchieh）從 2025 年 8 月的 iThome 鐵人賽系列到 2026 年 2 月的 blog 文章，建構了一套完整的論述：

**核心觀點一：Checking vs Testing**

AI 擅長的是「檢查（Checking）」——驗證預期結果，這是機械性勞動。但「測試（Testing）」是探索、實驗、批判性思考，目的是找出「未知」的風險。AI 解決了前者，但後者的瓶頸始終在人。

**核心觀點二：SDD 的三大限制**

Spec-Driven Development 的前提是規格夠好，但現實中規格永遠面臨三個問題：語言的模糊性（AI 讀得懂字但不懂語氣）、規格不可能寫全（冰山一角）、以及 domain know-how 無法自動推斷（行業潛規則）。

**核心觀點三：SBE 是補足 SDD 缺口的方法**

Specification by Example 透過具體範例把模糊需求轉化為可驗證的行為。Discovery 階段的 Example 目的是對齊業務理解、逼出規則、找出模糊地帶——不是測試腳本。

**核心觀點四：GenAI 的品質取決於引導方法**

直接問 AI 產出的 AC 品質最差，套用 Use Case Testing 中等，搭配 Decision Table Testing 最嚴密。最佳做法是組合使用：Use Case 建立故事骨架 → Decision Table 補強條件組合 → 人工審核業務邏輯。

**核心觀點五：測試思維是不可替代的前提**

測試思維包含三種能力：風險思考（哪裡最痛）、邊界判斷（關鍵例子）、行為視角（使用者真正想做的事）。沒有測試知識的人不知道要問對問題，GenAI 自然也不會主動幫你想到。

### 1.3 要解決的核心問題

> 能不能讓 AI 內建測試設計的方法論，在 SA/SD 階段主動引導人把需求中的灰色地帶逼出來，產出結構化的測試情境文件，同時銜接下游的開發與測試？

這等於把門檻從「你需要懂測試設計才能問對問題」降低到「你只需要懂業務就能回答 AI 的問題」。

## 三、AI 輔助 Discovery 的分層設計

### 3.1 四層處理模型

根據討論與柯仁傑方法論的整合，AI 輔助 Discovery 可拆為四個處理層次，每層的自主性和人機互動比例不同：

| 層次 | 名稱 | AI 自主度 | 人的角色 | 對應方法論 |
|------|------|-----------|----------|------------|
| L1 | 規格解構 | 高 | 提供輸入 | SDD 起點 |
| L2 | 灰色地帶偵測 | 中 | 回答問題 | SBE Discovery |
| L3 | 情境系統展開 | 高 | 刪減確認 | ECT / UCT / DTT |
| L4 | 領域知識補充 | 低 | 主動補充 | Domain Know-how |

#### L1：規格解構（AI 自主）

**輸入**：User Story、需求文件、API Spec、ER Diagram、既有程式碼

**處理**：
- 從自然語言中抽取結構化元素：Actor、Action、Rule、Constraint、Precondition、Postcondition
- 辨識業務物件及其狀態
- 辨識外部依賴與整合點
- 將規格轉為可機讀格式（YAML/JSON）

**產出**：結構化的規格摘要，作為後續所有展開的基礎

**範例**：

輸入 User Story：
```
身為一個經常搭乘高鐵的上班族
我希望能在列車發車前自行線上改票
以便於行程臨時變動時不必到櫃檯排隊
```

L1 解構產出：
```yaml
feature: 線上改票
actor: 經常搭乘高鐵的上班族
action: 在列車發車前自行線上改票
value: 行程變動時免去櫃檯排隊
identified_rules:
  - 需有時間限制（發車前多久可改）
  - 需有付款狀態前提（是否已付款）
  - 需處理票價差異（改到不同票價班次）
identified_objects:
  - 訂票紀錄（狀態：未付款/已付款/已取票/已使用）
  - 班次（出發時間、票價、座位）
identified_dependencies:
  - 付款系統（差額處理）
  - 座位系統（可用性查詢）
ambiguities:
  - 「發車前」的具體時間界線未定義
  - 票價差異的退補規則未定義
  - 是否限制改票次數未說明
```

#### L2：灰色地帶偵測（AI 提問，人回答）

**目的**：針對 L1 辨識出的模糊點，用精準的結構化問題向人確認

**AI 提問策略**（內建測試思維的提問框架）：

| 偵測模式 | 觸發條件 | 問題類型 |
|----------|----------|----------|
| 邊界偵測 | 看到數值條件 | 「發車前 X 分鐘」的 X 是多少？包含等於嗎？ |
| 時間偵測 | 看到時間相關描述 | 時區怎麼算？跨日（23:50 發車）怎麼處理？ |
| 狀態偵測 | 看到物件有多種狀態 | 在每種狀態下行為是否不同？ |
| 例外偵測 | 看到外部依賴 | 如果付款系統不可用怎麼辦？ |
| 併發偵測 | 看到共享資源 | 兩人同時改同一班次的最後一個座位？ |
| 業務風險 | 看到金額/個資/不可逆操作 | 改票涉及金額變動，退補規則是什麼？ |

**關鍵設計原則**：
- 每次提問控制在 3-5 個問題，避免資訊疲勞
- 問題按風險優先級排序（金額 > 安全 > 體驗 > 效能）
- 提供選項而非開放式問題（降低回答門檻）
- 明確標示「這個問題為什麼重要」

**範例互動**：

```
AI: 我分析了「線上改票」需求，有幾個關鍵點需要確認：

❶ 改票時間限制（風險：高 — 影響營運調度）
   「發車前可改票」的截止時間是？
   □ 發車前 30 分鐘  □ 發車前 60 分鐘  □ 其他：___
   ⚠ 為什麼重要：太晚允許改票會影響座位調度和售票

❷ 票價差異處理（風險：高 — 涉及金額）
   改到較高票價班次時：□ 補差額  □ 不允許
   改到較低票價班次時：□ 退差額  □ 不退差額  □ 不允許
   ⚠ 為什麼重要：直接影響退補款邏輯和財務流程

❸ 改票次數限制（風險：中）
   同一張票是否限制改票次數？
   □ 不限  □ 限 1 次  □ 限 N 次：___
```

#### L3：情境系統展開（AI 自主，人確認）

**目的**：一旦 L2 的規則被釐清，套用測試設計方法論做系統性展開

**三階段展開流程**：

**第一階段：Use Case Testing — 建立故事骨架**

從 L1 的結構化規格出發，展開主成功流程和例外流程：

```gherkin
# 主成功流程
Scenario: 發車前成功改票至同票價班次
  Given 使用者已完成訂票並付款
  And 距離發車時間超過 30 分鐘
  When 使用者選擇其他同票價班次並送出改票
  Then 系統完成改票並顯示新班次資訊

# 例外流程
Scenario: 發車前 30 分鐘內嘗試改票
  Given 使用者已完成訂票並付款
  And 距離發車時間小於等於 30 分鐘
  When 使用者嘗試改票
  Then 系統拒絕並顯示「距發車不足 30 分鐘，無法改票」
```

**第二階段：Decision Table Testing — 補強條件組合**

將所有規則交叉組合成 Decision Table：

```markdown
| # | 已付款 | 距發車時間 | 票價變化 | 可改票 | 系統行為       |
|---|--------|------------|----------|--------|----------------|
| 1 | 是     | > 30 分鐘  | 較高     | 是     | 補差額後改票   |
| 2 | 是     | > 30 分鐘  | 相同     | 是     | 直接改票       |
| 3 | 是     | > 30 分鐘  | 較低     | 是     | 改票，不退差額 |
| 4 | 是     | ≤ 30 分鐘  | 任意     | 否     | 拒絕改票       |
| 5 | 否     | 任意       | 任意     | 否     | 提示需先付款   |
```

**第三階段：State Transition — 狀態流轉覆蓋**

```markdown
## 訂票狀態轉移

| 起始狀態 | 動作     | 結果狀態 | 備註               |
|----------|----------|----------|--------------------|
| 已付款   | 改票成功 | 已付款   | 票券資訊更新       |
| 已付款   | 改票失敗 | 已付款   | 維持原狀           |
| 已付款   | 取消     | 已取消   | 觸發退款流程       |
| 已取票   | 改票     | —        | 需先退票再重新訂票 |
```

**覆蓋率自我檢查**：

L3 完成後，AI 自動執行覆蓋率分析：
- Decision Table 的所有條件組合是否都有對應 Scenario？
- 每個狀態轉換是否都有正向和反向測試？
- 有沒有 Happy Path 的例外路徑被遺漏？
- 邊界值（剛好 30 分鐘、剛好等於票價）是否被覆蓋？

#### L4：領域知識補充（人主導，AI 記錄）

**目的**：捕捉無法從規格推導的行業潛規則和業務慣例

**AI 的開放式提問**：

```
基於目前的規則定義，以下是一些我無法從規格推導、
但可能影響實作的領域知識問題：

1. 改票後的座位分配：是保留原座位類型（靠窗/走道）還是隨機？
2. 團體票改票：如果是 5 人以上團體訂票，改票規則是否不同？
3. 連假/尖峰時段：特定日期是否限制改票（如同早鳥票在連假不適用）？
4. 改票通知：改票成功後需要通知哪些人？（訂票人、同行者、接送者）
5. 與其他優惠的交互：如果原票有早鳥折扣，改票後折扣是否保留？
```

這些問題的回答會回饋到 L2 和 L3，觸發新一輪的展開。

## 四、結構化產出物定義

### 4.1 產出物架構

AI 輔助 Discovery 完成後，產出一份結構化文件，包含以下區塊：

```
📄 Test Specification Document
├── 1. Feature Summary（功能摘要）
│   ├── User Story
│   ├── 業務規則清單（已確認）
│   └── 未解決問題清單（待確認）
├── 2. Acceptance Criteria（驗收條件）
│   └── 以 Gherkin Given-When-Then 格式
├── 3. Decision Tables（決策表）
│   └── 條件組合矩陣
├── 4. State Transitions（狀態轉移）
│   └── 狀態圖 + 轉移規則表
├── 5. Test Scenarios（測試情境清單）
│   ├── 分類：Happy Path / Exception / Boundary / Concurrent
│   ├── 優先級：Critical / High / Medium / Low
│   └── 追溯：每個 Scenario 對應到哪條業務規則
├── 6. Test Data Conditions（測試資料條件）
│   └── 每個 Scenario 需要的資料前置條件描述
└── 7. Coverage Matrix（覆蓋矩陣）
    └── 規則 × Scenario 對應表
```

### 4.2 與下游的銜接格式

此產出物需能被 dotnet-testing-orchestrator 消費。建議格式為 JSON/YAML，結構如下：

```yaml
feature:
  name: "線上改票"
  user_story: "身為上班族，我希望能線上改票..."

rules:
  - id: R001
    description: "僅限已付款訂票可改票"
    confirmed: true
  - id: R002
    description: "距發車時間須大於 30 分鐘"
    confirmed: true
  - id: R003
    description: "改票至較高票價需補差額"
    confirmed: true
  - id: R004
    description: "改票至較低票價不退差額"
    confirmed: true

scenarios:
  - id: S001
    title: "發車前成功改票至同票價班次"
    category: happy_path
    priority: critical
    rules: [R001, R002]
    gherkin: |
      Given 使用者已完成訂票並付款
      And 距離發車時間超過 30 分鐘
      When 使用者選擇同票價班次並送出改票
      Then 系統完成改票並顯示新班次資訊
    test_data_conditions:
      - "訂票狀態 = 已付款"
      - "目標班次票價 = 原票價"
      - "當前時間距發車 > 30 分鐘"

  - id: S002
    title: "發車前 30 分鐘內嘗試改票被拒"
    category: boundary
    priority: critical
    rules: [R002]
    gherkin: |
      Given 使用者已完成訂票並付款
      And 距離發車時間等於 30 分鐘
      When 使用者嘗試改票
      Then 系統拒絕並顯示限制說明
    test_data_conditions:
      - "訂票狀態 = 已付款"
      - "當前時間距發車 = 30 分鐘（邊界值）"

decision_tables:
  - name: "改票可行性判斷"
    conditions: ["已付款", "距發車時間", "票價變化"]
    rules_matrix:
      - conditions: { 已付款: true, 距發車時間: "> 30 min", 票價變化: "較高" }
        action: "補差額後改票"
        scenario_refs: [S003]
      # ... 其他組合

state_transitions:
  - object: "訂票紀錄"
    transitions:
      - from: "已付款"
        action: "改票成功"
        to: "已付款"
        scenario_refs: [S001]

coverage_matrix:
  R001: [S001, S002, S005]
  R002: [S001, S002, S004]
  R003: [S003]
  R004: [S006]
```

### 4.3 下游消費方式

**對 orchestrator 的 Analyzer agent**：
- 讀取 scenarios 中的 gherkin 和 test_data_conditions
- 結合程式碼分析，定位 SUT 中對應的 class/method
- 將 scenario 的 category 和 priority 傳遞給 Writer agent

**對 orchestrator 的 Writer agent**：
- 根據 gherkin 的 Given-When-Then 產生 Arrange-Act-Assert 結構
- 根據 test_data_conditions 產生 AutoFixture 的客製化配置或 Builder pattern
- 根據 decision_tables 產生參數化測試（Theory/InlineData）

**對 orchestrator 的 Reviewer agent**：
- 使用 coverage_matrix 檢查：每條 rule 是否都有至少一個測試覆蓋
- 比對測試的 Assert 是否對應到 scenario 的 Then 條件
- 識別「綠色幻覺」：測試通過但 Assert 未驗證業務邏輯的情況

## 五、互動流程設計

### 5.1 完整流程

```
使用者提供需求文件
        │
        ▼
   ┌─────────┐
   │ L1 解構  │ ← AI 自主
   └────┬────┘
        │ 產出結構化規格 + 模糊點清單
        ▼
   ┌──────────────┐
   │ L2 灰色地帶   │ ← AI 提問，人回答
   │   偵測與確認   │   （3-5 題/輪，可多輪）
   └────┬─────────┘
        │ 規則確認完成
        ▼
   ┌──────────────┐
   │ L3 系統展開   │ ← AI 自主
   │  UCT → DTT   │
   │  → 狀態轉移   │
   └────┬─────────┘
        │ 展開結果 + 覆蓋率分析
        ▼
   ┌──────────────┐
   │ L4 領域知識   │ ← AI 提問，人補充
   │   補充（可選） │   （開放式問題）
   └────┬─────────┘
        │ 如有新規則 → 回到 L2
        ▼
   ┌──────────────┐
   │ 產出結構化    │
   │ 測試情境文件  │
   └────┬─────────┘
        │
        ▼
   ┌──────────────────────────────┐
   │ dotnet-testing-orchestrator  │
   │  Analyzer → Writer →        │
   │  Executor → Reviewer        │
   └──────────────────────────────┘
```

### 5.2 人機互動設計原則

- **AI 先做再問**：AI 先自主完成 L1 解構，帶著具體的分析結果去提問，而非丟出空泛的「請描述需求」
- **選擇題優先**：L2 的問題盡量提供選項，降低回答門檻
- **分批提問**：每輪 3-5 個問題，按風險排序，避免一次問 20 題導致使用者放棄
- **即時回饋**：每次人回答後，AI 即時展示更新後的規則和影響的 Scenario，讓人看到回答帶來的具體變化
- **可中斷**：任何階段都可以先產出「當前最佳版本」的文件，標註哪些規則尚未確認

## 六、與柯仁傑方法論的對齊

| 柯仁傑的方法論 | 本方案對應 | 差異 |
|---------------|-----------|------|
| SBE Discovery 會議 | L1 + L2 | 從面對面會議改為 AI 引導的結構化對話 |
| Example Mapping | L2 的提問策略 | AI 自動識別 Rule/Example/Question |
| Use Case Testing | L3 第一階段 | AI 自動展開主流程和例外流程 |
| Decision Table Testing | L3 第二階段 | AI 自動組合條件矩陣 |
| Equivalence Class Testing | L3 內建 | AI 對每個條件自動做等價劃分 |
| 人工審核業務邏輯 | L4 + 人確認 | 保留人在迴路中的角色 |
| 4 種 Prompt 格式 | 內建於 AI | 不再需要人知道用哪種 prompt |

**本方案的本質**：把柯仁傑教人的測試設計方法論，內建到 AI 的處理流程中，讓不具備測試設計知識的 SA/SD/開發人員，在 AI 的引導下也能產出有品質的測試情境。

---

## 七、實作路徑建議

### 7.1 階段一：概念驗證（Prompt Engineering）

不需要開發任何工具，用現有的 AI 對話（Claude / ChatGPT）搭配精心設計的 System Prompt，驗證 L1-L4 的流程是否可行。

核心驗證項目：
- 給定一份真實的 User Story，AI 能否自主完成 L1 解構？
- L2 的提問品質是否足以逼出關鍵規則？
- L3 的展開是否比直接問更完整？
- 產出的 YAML 格式是否能被下游消費？

### 7.2 階段二：Agent Skill 化

將驗證過的流程封裝為 GitHub Copilot 的 Agent Skill 或 MCP Server，讓它可以在開發環境中被呼叫。

### 7.3 階段三：整合 Orchestrator

將 Discovery Agent 作為 dotnet-testing-orchestrator 的前置 agent，形成完整的流水線。Reviewer agent 同時升級，加入需求追溯的審查能力。

---

## 八、風險與限制

| 風險 | 說明 | 緩解措施 |
|------|------|----------|
| AI 產出的情境看似完整但偏離業務 | 柯仁傑指出的「看似厲害但毫無測試價值」 | L4 的領域知識補充 + 人始終在迴路中 |
| 使用者不願回答太多問題 | 互動疲勞導致放棄使用 | 控制每輪問題數、提供選項、允許跳過 |
| 格式不被下游工具接受 | YAML/JSON 結構不符合 orchestrator 期望 | 階段一就定義好 schema 並做端對端驗證 |
| 過度依賴 AI 降低團隊測試思維 | 長期可能弱化團隊自身的測試設計能力 | 將 AI 的提問邏輯透明化，作為學習工具 |

---

## 九、結論

本方案的核心價值不在於「讓 AI 替人想測試情境」，而在於：

> **讓 AI 帶著測試設計方法論去引導人，把人腦中已有的業務知識和直覺，系統性地轉化為結構化的測試情境。**

這與柯仁傑的立場完全一致：AI 是加速器，不是思考者。差別在於，本方案把測試設計的「思考框架」預先灌進 AI，使它成為一個帶著方法論的加速器——降低測試思維的入門門檻，同時保留人在關鍵判斷上的不可替代性。

當這段補上之後，完整的流水線就從 SA/SD 階段一路貫穿到測試執行與審查，實現需求到驗證的全鏈路追溯。
